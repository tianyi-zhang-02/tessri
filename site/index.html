Keep code understandable.

Agents write more of the code; people still have to stand behind it. Tessri reads a codebase and its git history, offline and with nothing else installed, and tells the person a change is handed to where to look first, who is able to look, what it did to the structure, and what nobody maintains, with the evidence for every claim.

Where to look first, who is able to look, what the change did to the structure, which tests reach it and which checks ran, and what needs a person: from one analysis of the base and one of the working tree, with the evidence for every line.

  3. ValidationThe tests that reach the change, kept apart from the checks the host recorded as run.
  4. Open for a personWhat the analysis cannot settle: a decision, a second reader, a check nobody ran.

How does it work?

One pass over the files and the history, then one view per question.

No model, no network, no service, and it never edits your code. The order triage puts files in was backtested on real history; the composite risk score we tried did not beat its parts, so there is none.

{{icon:file-search}}01

Read

Lists the files, parses Python with Python's own parser and JavaScript and TypeScript with its own scanner, and reads configs, scripts and docs for the files they name.

{{icon:git-merge}}02

Join

Builds the import graph with the kind of evidence behind every edge, and reads from git who changed what, following files through renames.

Each command is one view of that picture: reachability, ownership, module graph, impact, triage and the check of a change.

Evidence, not adjectives

Every claim can be traced, and what the analysis cannot see it says it cannot see.

17 test files reaching it (candidates to run, not runs)tessri impact
13 names in configs, scripts or code fit several files each and so name none of them: utils.py (15), config.py (12), …tessri scan, caveats
Dependencies are static imports between files of this repository. A deleted or moved file that an untouched config, script or document still names, or that untouched code still names in a string or a dynamic import, is reported with the kind of each name; a name in a string is a guess that the file is loaded at run time, so that one is for a person. Registries and consumers outside the repository are invisible, so a clean result does not mean nothing else depends on the change.tessri check
Getting started

Three steps.

  1. Scan a repository. tessri scan . prints the report; --format html --out report.html writes one offline page with the explorer.
  2. Ask before, during and after a change. tessri impact <path> before, tessri triage to review one, tessri check when it is done, tessri brief to hand it over on one page; without --since, a branch is judged against the default branch.
  3. Give it to your agent, and to every pull request. tessri integration install --agent claude (or codex) installs the skill with a receipt, --agent review posts the brief on every pull request; tessri integration remove takes it all out again.
